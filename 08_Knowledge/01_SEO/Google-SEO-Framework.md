# Google SEO Framework for Industrial B2B Websites

> Internal execution rules for Codex. Apply this framework when auditing, planning, creating, or optimizing an overseas English-language website for an industrial manufacturer.

## 1. SEO Objective Definition

SEO must support qualified industrial buyer acquisition and commercial growth. Traffic, impressions, and rankings are diagnostic metrics, not the final objective.

### 1.1 Required business inputs

Before starting any SEO task, Codex must confirm or document:

- Target countries, regions, and English variant
- Priority product families, models, solutions, and applications
- Target buyer roles: engineer, procurement manager, project owner, OEM, integrator, distributor, or maintenance team
- Buyer requirements: specifications, standards, compatibility, customization, quality, delivery, documentation, and support
- Primary conversions: RFQ, application consultation, contact, call, email, sample request, technical download, or distributor inquiry
- Available evidence: product data, drawings, certifications, tests, cases, engineering knowledge, and manufacturing capability
- Data sources and periods: GSC, GA4, CRM, crawl data, sales inquiries, and content inventory

If these inputs are unavailable, Codex must state the limitation and avoid presenting assumptions as facts.

### 1.2 SEO success hierarchy

Evaluate performance in this order:

1. Priority pages can be crawled, rendered, indexed, and measured.
2. Pages match real buyer intent in target markets.
3. Search visibility reaches relevant product, solution, and application queries.
4. Visitors progress to technical evaluation and commercial pages.
5. Organic traffic generates qualified inquiries or assists opportunities.
6. Content and architecture create sustainable coverage around the company’s real expertise.

### 1.3 Required KPI model

| Layer | Required examples |
|---|---|
| Technical eligibility | Valid canonical URLs, intended indexation, renderability, tracking quality |
| Search visibility | Non-brand impressions/clicks, target-country queries, priority page visibility |
| Buyer engagement | Product/solution progression, downloads, engaged sessions, CTA/form starts |
| Conversion | RFQs, calls, emails, technical consultations, qualified inquiries |
| Business quality | Qualified-lead rate, opportunity value, product/market fit where CRM data exists |

Codex must not promise rankings, traffic, leads, or revenue.

## 2. Understanding Google Search Systems

Codex must work from these operational principles:

### 2.1 Search is a process

Evaluate pages across four stages:

1. **Discovery:** Google can find the URL through crawlable internal links or other discovery signals.
2. **Crawling and rendering:** Google can access required resources and render primary content.
3. **Indexing and canonicalization:** Google can understand the page, select a representative URL, and determine whether it belongs in the index.
4. **Serving and ranking:** Google evaluates relevance, usefulness, quality, context, and many other signals for a specific query.

Passing technical checks does not guarantee crawling, indexing, or ranking.

### 2.2 Google uses multiple systems and signals

- Google systems interpret concepts, language, passages, query intent, links, originality, freshness where relevant, and other page/site signals.
- Most evaluation is page-level, while some site-wide signals and classifiers may contribute.
- Exact keyword repetition is not required for Google to understand related concepts.
- Links help discovery and understanding, but internal linking must first serve navigation and context.
- Freshness matters only where the query expects current information; changing dates without meaningful updates is prohibited.
- Core updates should trigger evidence-based review of affected pages and queries, not speculative mass rewriting.

### 2.3 Mandatory operating rules

Codex must:

- Build pages around buyer intent and complete answers, not individual keyword variations.
- Use terminology buyers use in titles, headings, body copy, image context, and links where natural.
- Maintain one preferred canonical page for each primary intent.
- Produce original industrial value using verified product and engineering knowledge.
- Follow Google Search Essentials and spam policies.
- Treat AI as a production tool, not as a substitute for sources, expertise, review, or buyer value.

Codex must not:

- Chase a rumored single ranking factor.
- apply arbitrary word counts, keyword density, or publishing frequency.
- Create scaled low-value pages to manipulate search visibility.
- Copy, lightly rewrite, or summarize competitors without adding original value.
- Add hidden text, link schemes, doorway pages, fake freshness, or misleading structured data.

## 3. Page Quality Evaluation Standard

A page passes only when it is technically eligible, intent-matched, complete enough for its buyer task, trustworthy, usable, and connected to a next step.

### 3.1 Quality scorecard

Score each dimension from 0–2:

- **0 — Fail:** missing, incorrect, unsupported, or harmful
- **1 — Partial:** present but incomplete, generic, weakly supported, or difficult to use
- **2 — Pass:** complete for the page’s purpose, specific, verified, and usable

| Dimension | Pass standard |
|---|---|
| Business purpose | Supports a priority product, solution, market, or buyer need |
| Search intent | Page type and content match the primary query task |
| Buyer completeness | Buyer can complete the intended evaluation step without searching again for basic information |
| Original value | Contains company-specific technical knowledge, data, process, evidence, or decision support |
| Technical accuracy | Specifications, units, standards, claims, and compatibility are verified |
| Trust | Company identity, sources, proof, authorship/review, limitations, and contact path are clear |
| Page structure | Title, H1, headings, modules, tables, media, and CTA follow decision logic |
| Internal links | Parent, child, supporting, evidence, and conversion paths are logical |
| Technical eligibility | Status, robots, canonical, rendering, mobile, metadata, and schema are correct |
| Experience | Content is readable, accessible, responsive, stable, and functional |
| Conversion | Next step matches the buyer stage and is measurable |

### 3.2 Quality decision

- **Critical fail:** crawling, indexing, tracking, form, security, or factual-integrity issue; fix before growth work.
- **Rewrite required:** intent mismatch, thin decision value, unsupported claims, or substantial duplication.
- **Improve:** correct purpose but incomplete content, proof, links, usability, or conversion.
- **Pass:** no critical failures and every required dimension scores 2.

Do not average away a critical failure with strong scores elsewhere.

## 4. Topic Cluster Strategy

### 4.1 Cluster model

Build clusters around real commercial entities and buyer problems:

`Commercial hub ↔ Pillar/selection resource ↔ Supporting articles/FAQs ↔ Products/Solutions/Cases/Downloads ↔ Inquiry`

The commercial hub may be a category, solution, or application page. Do not create a blog pillar automatically when a commercial page is the correct target.

### 4.2 Required cluster fields

For each cluster, define:

- Product/solution and business priority
- Target buyer, market, and industry
- Primary problem or decision
- Buyer stages: discover, compare, validate, specify, implement, maintain, or source
- One preferred URL for each distinct intent
- Required technical sources and reviewer
- Internal-link relationships
- CTA and conversion path
- Baseline and measurement plan

### 4.3 Topic acceptance rules

Approve a topic only when:

- It reflects a real buyer question or decision.
- It connects to an actual product, solution, capability, or service.
- The company can provide accurate, differentiated information.
- It has a distinct intent and page boundary.
- It has a clear internal-link and next-step plan.

Reject topics based only on search volume, trends unrelated to the business, trivial keyword variations, or content the company cannot verify.

### 4.4 Cannibalization control

Flag two or more pages when they share the same intent, similar titles/H1s, overlapping GSC queries, competing internal anchors, or substantially duplicated answers. Before merging, redirecting, canonicalizing, repositioning, or removing a page, check conversions, backlinks, market/language purpose, rankings, and URL dependencies. URL changes require approval.

## 5. Page Hierarchy Strategy

### 5.1 Preferred hierarchy

`Homepage → Product Category / Solution Hub → Product Detail / Solution / Application → Case Study / Blog / FAQ / Resource → Inquiry`

### 5.2 Page roles

| Page type | Primary role |
|---|---|
| Homepage | Establish company/product relevance and route buyers |
| Product category | Explain a product family and support comparison/selection |
| Product detail | Validate a specific product/model and support RFQ |
| Solution/application | Solve an industry, process, system, or operational problem |
| Case study | Provide verified implementation evidence |
| Blog/guide | Answer a defined informational, evaluation, or implementation task |
| FAQ | Resolve a narrow recurring question |
| Resource | Deliver datasheet, drawing, manual, certificate, or technical evidence |

### 5.3 Hierarchy rules

- Every priority indexable page must have at least one crawlable inlink from an indexable page.
- Priority commercial pages should normally be reachable within three logical clicks from the homepage.
- Breadcrumbs must reflect a useful user path.
- Category pages link to products and relevant solutions; product pages link to their category, solutions, evidence, and inquiry; informational pages link to an appropriate commercial next step.
- Orphan pages, dead ends, uncontrolled filters, duplicate parameters, and inconsistent locale paths must be flagged.
- XML sitemaps do not replace internal links.

## 6. Product Page SEO Rules

A product page must help an engineer or buyer determine fit and initiate an informed inquiry.

### 6.1 Required content

- Exact product/model identity and parent category
- Clear intended applications and operating context
- Verified features connected to buyer value
- Specifications with units, standards, ranges, and revision-controlled sources
- Standard, optional, custom, and incompatible configurations separated
- Materials, dimensions, ratings, interfaces, compatibility, and limitations where applicable
- Approved images, drawings, datasheets, manuals, CAD, certificates, or tests
- Manufacturing, quality, customization, and support evidence relevant to the product
- Product-specific FAQ and related solution/case/resource links
- RFQ path that preserves product/model context

### 6.2 SEO and technical rules

- One product-detail intent per canonical page.
- Unique title, H1, description, and visible opening.
- Do not copy category metadata or generic supplier copy.
- Do not place all useful information only in a PDF.
- Product schema must match visible, verified data; do not invent price, stock, rating, review, GTIN, or offer data.
- Variant URLs require an intentional canonical/index strategy.
- Discontinued products require a buyer- and data-informed status/redirect strategy, not automatic homepage redirection.

### 6.3 Product page failure conditions

- Unverified or inconsistent specifications
- No application/selection guidance
- Claims or certification not applicable to the model
- Duplicate pages for keyword or parameter variants
- Product image or schema describing a different configuration
- RFQ form loses product context

## 7. Solution Page SEO Rules

A solution page must address a defined industry, process, application, system, or operational problem. It is not a renamed product list.

### 7.1 Required content

- Target buyer and operating challenge
- Environment, inputs, constraints, standards, and success criteria
- Solution approach, architecture, workflow, or selection logic
- Relevant products and the function of each product in the solution
- Integration, compatibility, implementation, and support requirements
- Technical value with evidence and conditions
- Limitations, assumptions, trade-offs, and project-specific validation boundaries
- Approved diagrams, cases, tests, standards, and technical resources
- Project inquiry form requesting the inputs required for evaluation

### 7.2 SEO rules

- Target problem/application intent rather than duplicating a product/category intent.
- Use terminology of the target industry and market accurately.
- Link to relevant product pages instead of duplicating complete specifications.
- Link to supporting cases, guides, FAQs, and resources.
- Avoid templated industry pages where only the industry name changes.
- Do not guarantee savings, safety, compliance, performance, or project outcomes.
- Preserve application context through the consultation journey and analytics events.

## 8. Blog Content Strategy

### 8.1 Valid blog roles

Use blog/guide content to support:

- Product and technology education
- Type/material/technology comparison
- Selection, sizing, configuration, and specification preparation
- Standards, testing, quality, and compatibility explanation
- Installation, integration, commissioning, maintenance, and troubleshooting
- Supplier evaluation, documentation, and RFQ preparation

### 8.2 Production rules

Every article requires:

- Defined market, buyer, intent, stage, and business connection
- One core question and preferred canonical URL
- Approved sources and technical reviewer
- Original value such as engineering logic, test method, decision table, diagram, process knowledge, or verified experience
- Clear assumptions, units, conditions, limitations, and safety boundaries
- Links to its cluster hub, relevant commercial page, supporting content, and CTA

### 8.3 Prohibited blog practices

- Publishing generic “what is” articles unrelated to a commercial capability
- Mass-producing keyword variations or lightly rewritten competitor content
- Using fixed word count as a quality target
- Writing unsafe machinery/electrical instructions without qualified review
- Claiming compatibility, compliance, performance, or results without evidence
- Changing dates without meaningful content updates
- Ending an informational page without a relevant buyer path

### 8.4 Maintenance

Review articles when product data, standards, linked pages, search intent, or buyer questions change. Update, consolidate, redirect, or retire only after evaluating traffic, links, conversions, and dependencies.

## 9. Practical E-E-A-T Implementation

E-E-A-T is not a standalone score or a single ranking factor. Codex must use it as a trust and quality audit model. Trust is the controlling requirement.

### 9.1 Experience

Demonstrate real operational experience through approved:

- Application conditions and constraints
- Installation, commissioning, maintenance, or troubleshooting knowledge
- Process photos, test setups, drawings, samples, and production evidence
- Case studies with challenge, method, conditions, and verified results
- Trade-offs, failure modes, lessons learned, and limitations

Do not simulate first-hand experience.

### 9.2 Expertise

- Identify qualified authors or technical reviewers where readers expect them.
- Link bylines to profiles showing role, relevant experience, and subject scope.
- Use correct standards, terminology, calculations, units, and revision-controlled sources.
- Require qualified review for machine safety, electrical safety, pressure, load, thermal, chemical, regulatory, or other high-risk guidance.
- State when project-specific engineering validation is required.

### 9.3 Authoritativeness

- Build focused coverage around the company’s real products and industries.
- Publish original technical resources, research, test methods, case evidence, and documentation.
- Maintain consistent company, product, author, and organization identity.
- Earn relevant references through real partnerships, industry bodies, distributors, customers, publications, and useful resources; do not buy or fabricate authority signals.

### 9.4 Trust

- Provide clear company identity, address/contact channels, legal/privacy information, and actual business role.
- Scope certifications, standards, warranties, capabilities, customer claims, and commercial terms accurately.
- Cite or identify source basis for technical and quantitative statements.
- Show publication/review/update information where useful; do not fake freshness.
- Separate measured results, customer-reported results, supplier observations, and estimates.
- Explain content creation methods or AI assistance when a reader would reasonably expect disclosure.
- Correct errors and outdated information promptly.

### 9.5 E-E-A-T evidence checklist

- [ ] Content creator and technical reviewer are identifiable where appropriate
- [ ] Author/reviewer qualifications match the topic
- [ ] Technical sources and revision dates are recorded internally
- [ ] Original company experience or evidence is present
- [ ] Claims, cases, images, certifications, and results are approved
- [ ] Limitations and project-specific variables are disclosed
- [ ] Company identity, policies, and contact paths are clear
- [ ] AI-assisted content has human source verification and technical review

## 10. Page SEO Checklist

Codex must complete this checklist for every priority page audit or optimization.

### 10.1 Objective and intent

- [ ] Page type, target buyer, market, English variant, intent, stage, and conversion are defined
- [ ] Page supports a priority product, solution, application, or business need
- [ ] One preferred canonical page serves the primary intent
- [ ] SERP/page-type fit and internal cannibalization were checked

### 10.2 Content quality

- [ ] Title, H1, opening, sections, and CTA represent the same purpose
- [ ] Page answers the buyer’s required decision questions
- [ ] Product facts, units, standards, compatibility, and claims are verified
- [ ] Original technical or commercial value is present
- [ ] Assumptions, limits, risks, and required validation are stated
- [ ] No unsupported superlatives, fake evidence, keyword stuffing, or internal SEO language is visible

### 10.3 Structure and internal links

- [ ] Heading hierarchy and module order follow buyer decision logic
- [ ] Parent, child, related, evidence, and conversion links are present
- [ ] Anchors are descriptive and destinations are canonical
- [ ] Page is not orphaned or a buyer dead end
- [ ] Breadcrumbs and navigation reflect the intended hierarchy

### 10.4 Technical eligibility

- [ ] Intended status code, robots directive, canonical, and sitemap state are correct
- [ ] Primary content and crawlable links exist in rendered HTML
- [ ] Mobile and desktop contain equivalent primary content and metadata
- [ ] Title, description, language, hreflang, and structured data are valid where applicable
- [ ] Duplicate URL variants and parameters are controlled
- [ ] Forms, downloads, navigation, tracking, consent, and conversion events work
- [ ] Core Web Vitals and page-experience risks were checked using appropriate evidence

### 10.5 E-E-A-T and conversion

- [ ] Creator/reviewer, sources, experience, proof, and company identity are sufficient for the topic
- [ ] Certifications, cases, statistics, and customer references are approved and correctly scoped
- [ ] CTA matches the buyer stage and preserves page/product/solution context
- [ ] Conversion path is measurable

### 10.6 Required Codex output

For every analysis, provide:

1. Objective, URL scope, market, and data period
2. Data sources, evidence, and limitations
3. Findings labeled as observed, inferred, or requires validation
4. Priority: Critical, High, Medium, or Low
5. Recommended action and affected URL/file/template
6. Dependency, risk, and approval requirement
7. Validation method and measurement plan
